# Review 2026-11-17: performance, UI and usability, tests

Read: all of `lib/`, the tests, PLAN.md, CLAUDE.md. Compared with `~/ws/nvimos-ops` (Ops), the
project Purrage copies its keys, code shape and test rules from. Ran the suite once with
`--coverage` (105 tests, 2 min). Each suggestion is a Backlog task; this page is the map.

## Performance

The optimistic actions and the "no polling" rule are right. What is left is work that grows
with the number of rows, or the size of the selection, where it should not.

| task | what | where |

## Design and implementation principles (from Ops)

The two rule sets Ops holds itself to: the **design** principles in `nvimos-ops/PLAN.md`
"Style and theme" (one source for the look, small named scales, visible focus, contrast, never
colour alone), and the **implementation** principles in `declarative_ui_guidelines.md` plus Ops'
CLAUDE.md "UI code" (nesting ≤ 3, `build` < 50 lines, no logic in handlers, dumb atoms, Flutter's
own elements, explicit cursor and tooltip). Each set has one task, as a checklist.

| task | what |
|---|---|
| task-20 | **Design**. The palette is in `theme.dart`, but the rest of the look is inline: 21 `fontSize:` literals (sizes from 9.5 to 13; text under 11 px), 16 `fontFamily: 'monospace'` (which Windows may not map to a monospaced font), radii 3/4/5/6/8, icon sizes 15–18, alpha tints computed in widgets, and Material ripples instead of a hover token. Nothing marks the pane that has the keys. Console failures are told apart by colour alone. Tooltips do not name their keys. |
| task-21 | **Implementation**. `build` over 50 lines in `_RepoRow` (72), `FileList` (56) and `NoticeBar` (55). `RowTile`/`ShellState` nest 6+ levels. Five row handlers in `file_list.dart:146` hold a selection rule. The Tooltip + MouseRegion + InkWell atom is hand-built about 16 times (port Ops' `widgets.dart`: `HoverRow`, `SmallButton`, `LinkButton`, `Pill`, `PaneHeader`). Keys are an if-chain where `Shortcuts`/`Actions`/`Intent` would also generate the help table. |

## Tests and coverage

Design: `openspec/changes/test-coverage-and-integration/`, tasks task-16 and task-17.

Baseline: **63.8% of lines** (1602 / 2511), and `main.dart` is never loaded. Lowest:
`theme` 0%, `diagnostics` 4%, `notices` 13%, `browser` 21%, `notice_bar` 27%, `failure` 29%,
`browse_view` 46%, `filter_field` 47%, `changes` 49%, `shell` 53%, `editors` 54%,
`settings_view` 58%. `ignore_rules`, `paths`, `commit_bar`, `help_view` and `nav_keys` are at 100%.

- **Unit, to 100%**: `make coverage` + `tool/coverage.dart` (no new package). It lists files never
  loaded, honours `coverage:ignore` markers only with a reason, prints terse action-first lines,
  and fails below `MIN=100`. The new tests mostly depend on task-14 and task-15. The rest needs
  `FakeRepo` failure switches and `fakeAsync` for the notice timer.
- **Integration, critical flows**: `integration_test/` on `-d windows`, real git in temp repos,
  real keys, asserting the screen *and* git's answer. Run locally with `make itest`, not part of
  `make test`. Ten flows: start, track/untrack, quick ignore, ignore dialog into a nested file,
  hidden `.gitignore`, commit, failure reporting (index.lock), reload with no polling, Browse
  switch, nested repository.

## How the later work runs

One worktree per task (or per wave-2 sequence), started from **local** `main`, not `origin/main`
(Ops rule: local main has unpushed commits), in its own session. Finish with `/prish`, merge
with `/prish-merge`. Per CLAUDE.md: `flutter analyze` after each edit, tests and builds only when
asked or when a change cannot be verified otherwise, one commit per feature.
